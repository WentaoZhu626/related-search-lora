# 相关搜索推荐实验总结

Qwen3-4B-Instruct-2507 + LoRA + 判断头，near-OOD 划分实验与全量部署模型。本文档汇总实验思路和过程中产生的关键结果，独立于旧的 `model_training/` 代码。

## 1. 数据

底层数据是 `cleaned_dataset.csv`，已经过清洗，共 **19,847 条**，每条包含一个 query 和最多 11 个人工标注的相关搜索词（没有相关词的行代表"不该展示相关搜索"）。

从全量训练时的统计看，数据分布是这样的：

| | 总数 | 正样本（有相关词） | 正样本占比 | 平均 token 长度 | 最长 token |
|---|---|---|---|---|---|
| 训练集 | 19,347 | 14,757 | 76.3% | 207.2 | 260 |
| 留出验证集 | 500 | 379 | 75.8% | 207.3 | 240 |

两点可以说明数据分布是合理、可信的：

- **训练集和验证集的正样本占比几乎一致**（76.3% vs 75.8%），说明数据划分没有引入偏差，随机切分是有效的。
- **训练时没有任何样本因为超长被截断丢弃**（`dropped_too_long = 0`），设定的 `max_length=384` 完全覆盖了数据的实际长度分布，不存在因截断丢失结束符导致的隐性数据损坏。

## 2. 模型与训练方法

- **底座模型**：Qwen3-4B-Instruct-2507，全部参数冻结。
- **LoRA**：在注意力和 MLP 的关键投影层（q/k/v/o、gate/up/down_proj）插入低秩矩阵，rank=16，只训练这一小部分新增参数，原模型一个参数都不改。
- **判断头（gate head）**：额外训练的小分类器，接在最后一层隐藏状态（prompt 最后一个 token 的位置）上，判断"这个 query 要不要展示相关搜索"，与 LoRA 一起训练、一起保存。
- **联合损失**：`L = 生成损失 + 门控损失`，两部分权重各占 1.0。
- **system prompt**：随 adapter 一起保存版本号和内容，保证评估、体验、以后部署用的都是训练时那一份，不会因为代码里后来改了 prompt 而错配。

## 3. Near-OOD 实验（验证泛化能力）

在正式拿全部数据训练部署模型之前，先做了一次专门验证泛化能力的实验，思路是：**故意把一部分语义主题从训练集里整体拿掉，看模型在完全没见过的主题上表现如何**，而不是只看随机切分出来的、跟训练数据高度同分布的测试集。

具体做法：

1. 对全部 query 做语义向量聚类（spherical K-means，40 个簇）。
2. 自动挑选出规模、正样本率、离群程度都满足条件的若干个簇，整体作为 `test_ood`（模型训练时完全没见过这些主题）。
3. 在 `test_ood` 周围设一圈"缓冲带"，把语义上跟它太接近的训练候选也一并去掉，避免 OOD 集其实跟训练集很像、测试失去意义。
4. 剩下的数据再随机分层切出 `validation`（用来选门控阈值）和 `test_id`（跟训练集同分布的测试集，作为对照）。

**划分是否真的有效**：检查了 `test_ood` 相对训练集的"最近邻相似度"和"标准答案词在训练集中出现过的比例"，两者都明显低于 `test_id`，说明这次划分确实把 OOD 集推得更远，不是伪 OOD（如果两边数值接近，说明簇选得太近，划分没起作用）。

**训练过程中发现并修复了一个真实的正确性 bug**：`transformers` 新版本在检测到梯度累积时会自动计算 `num_items_in_batch` 并接管归一化逻辑，而自定义的 `compute_loss` 没有对这个参数做处理，导致反向传播时梯度被放大了「梯度累积步数」倍（这里是 4 倍），相当于有效学习率被意外放大。这个 bug 是从训练日志里 `loss` 字段和手动记录的 `lm_loss+gate_loss` 对不上、比例正好是 4 倍这个细节发现的，修复后在本地玩具模型和真实 GPU 训练日志上都验证了 `loss` 精确等于 `lm_loss+gate_loss`。

**评估结论**：门控和生成质量在 ID / OOD 两边确实有一些差距，但结合 bootstrap 95% 置信区间来看，大部分差距在统计上不构成需要担心的显著退化——不是"模型在陌生主题上崩了"，是正常的、可预期的泛化衰减幅度。结论范围：只代表"同一 Pinterest 风格分布内、训练时没见过的语义主题"，没有真实线上 query 和教师标注做不了更远的 OOD。总体判断：**泛化情况健康，可以推进到用全部数据训练部署模型这一步**。

## 4. 全量重训（用于部署的最终模型）

OOD 实验只是为了拿到"泛化没问题"这个结论，真正要部署的模型用全部数据（`train` + `test_id` + `test_ood` + 缓冲带数据全部并回训练集，`validation` 继续留出不参与训练）重新训练了一次，超参数与 OOD 实验保持一致。

| 指标 | 数值 |
|---|---|
| 训练样本 | 19,347（正样本 76.3%） |
| 训练耗时 | 4,728 秒（约 1.3 小时），3 epoch |
| 最终 train_loss | 1.379 |
| 验证集 eval_loss | 1.587 |

**门控阈值的确定方式**：训练结束后，用留出的验证集（500 条）跑一遍门控概率，穷举验证集上出现过的每一个概率值作为候选阈值，选 `balanced_accuracy =（recall + specificity）/2` 最高的那个（用 balanced accuracy 而不是普通 accuracy，是因为正样本占 76%，普通 accuracy 容易被数据不平衡"作弊"）。这次自动选出的阈值是 **0.9656**，对应 precision 0.97 / recall 0.76（precision 0.9696，recall 0.7573，specificity 0.9256，balanced accuracy 0.8414，f1 0.8503；tp=287, fp=9, tn=112, fn=92）——这个阈值本质是"宁可少展示、也不乱展示"的保守操作点，跟产品实际想要的展示覆盖率不一定匹配，所以最终**手动调整为 0.85**，在"少漏报"和"少误报"之间做了更符合直觉的折衷（这一步不需要重新训练，只是改了 `final_adapter/gate_config.json` 里的阈值字段）。

补充说明一下项目过程中出现过的几个不同阈值，避免混淆：训练迭代早期（bug 修复之前）曾出现过 0.3076 这样偏低的阈值，那是修 bug 之前的中间产物；OOD 实验（bug 修复后、正式评估）选出的阈值是 0.8555；这次全量重训自动选出 0.9656，最终手动定为 0.85 上线体验。数字会随每次训练的数据、随机种子而变化，属于正常现象。

## 5. 已知问题与待验证事项

- **生成阶段发现过复读问题**：手动体验时，"花园"这个 query 生成结果陷入了"花园别墅 | 花园 | 花园 ..."的复读循环，最后因为达到最大生成长度被截断，解码出乱码字符。原因是当前默认的 `repetition_penalty=1.0`（为了不惩罚"红色/红裙"这类合理重复字，特意没有默认开启惩罚），个别 query 会因此陷入贪心解码的复读循环。临时缓解办法是生成时加 `--repetition-penalty 1.05~1.15`；系统性排查建议用 `evaluate_gate.py` 的"输出健康度"指标在验证集上统计整体的重复输出率，判断是个别现象还是普遍问题，目前还没有正式跑过这个健康度统计。
- **面向陌生主题的人工抽查**：另外准备了一批数据集里逐字确认过从未出现过的 query（一组是主题贴近但说法陌生的"类内泛化"用例，一组是完全跳出生活方式类目的"域外拒绝"用例），用来手动感受一下全量模型的泛化边界。实测下来主观感受是**泛化效果不错**，这批陌生 query 上的表现符合预期，进一步印证了第 3 节里"泛化健康"的结论不是只停留在统计指标上，人工抽查也站得住。
- **体验/部署通道已经打通**：`demo_app.py` 提供网页体验界面，在 AutoDL 公网直连受限的情况下，最终确认可行的方案是 SSH 端口转发（mentor 在自己电脑本地跑一条 SSH 命令转发端口，浏览器打开 `localhost` 即可体验），不依赖任何需要跨境访问的服务。

## 6. 小结

这套 pipeline 从数据划分、训练、评估到部署体验走完了一整条链路：用语义簇留出的方式专门设计了一次近似 OOD 的实验去验证泛化能力而不是只看同分布测试集；训练过程中发现并修复了一个真实的梯度累积 bug，避免了错误的有效学习率；OOD 结果显示泛化情况健康后，才用全部数据重新训练了要部署的最终模型；门控阈值的选择方法有明确、可解释的统计依据，且可以脱离重新训练直接调整以适配产品对精确率/召回率的实际偏好。目前处于让 mentor 亲自体验、收集主观反馈的阶段。
